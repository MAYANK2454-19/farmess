# Farmer consent audit event contract

This module converts a persisted farmer consent snapshot plus a partial consent update into an ordered set of audit events. It is a pure event builder; it does not write to a database.

## Audited consent fields

- `approximateLocationSharing`
- `exactLocationDisclosure`
- `buyerContactDisclosure`
- `providerContactDisclosure`

Each event records only:
- Actor and farmer user IDs.
- Consent field and broad data category.
- Previous and next boolean value.
- Grant or revoke event type.
- Server-generated event timestamp.
- A stable deduplication key.

It does not store phone numbers, contact strings, locality text, GPS coordinates or other private profile values.

## Rules

- Only the farmer themselves may change their own consent preferences.
- The previous consent snapshot must be loaded from trusted persistence.
- Only the four supported boolean fields can be patched.
- Fields omitted from the patch are unchanged.
- An explicit false value is a revocation.
- Unchanged values produce no event.
- Multiple changes are returned in deterministic consent-field order.
- Timestamps must be generated by server code, not copied from request JSON.

## Persistence integration

When the shared Supabase project/schema is available, persist events in an append-only consent audit table with:
- Generated primary key.
- Actor and farmer foreign keys.
- Consent field, prior value and next value.
- Event type and server timestamp.
- Unique dedupe key.

Enable RLS so farmers can inspect their own consent audit history, but browser users cannot forge or update audit events. The server should insert audit events in the same transaction as the consent preference update; a failed audit write must not leave the settings changed without an audit trail.

## Integration boundary

The caller should:
1. Authenticate the farmer using the verified server-side session.
2. Load the current consent snapshot.
3. Parse the profile PATCH using the profile request boundary.
4. Build audit events using this module and a server timestamp.
5. Persist the changed preferences and audit events atomically.
6. Re-evaluate the disclosure policy for all later data access.

This PR contains no SQL migration, Supabase client or profile route because the shared database has not been provisioned for this workspace.
